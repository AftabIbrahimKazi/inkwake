# Inkwake — Anime E-Commerce CSS Benchmark — Project Plan

## Brand Name
**Inkwake** — chosen for the anime-themed storefront concept; ties directly into the ink cursor effect (Step 2) as a signature brand touch. Used as:
- GitHub repo name: `inkwake`
- Vercel project naming convention: `inkwake-tailwind`, `inkwake-bootstrap`, `inkwake-strata`
- Suggested live domain naming: `tailwind.inkwake.com`, `bootstrap.inkwake.com`, `strata.inkwake.com` (or equivalent `*.vercel.app` subdomains if no custom domain is attached: `inkwake-tailwind.vercel.app`, etc.)

## Goal
Build the identical landing page three times — once each in Tailwind CSS, Bootstrap, and Strata CSS — deployed to three separate live domains, to measure real-world load speed (Core Web Vitals: LCP, TBT/INP, CLS) under identical JS logic, identical content, identical DOM intent. Only the CSS framework (and its native JS idiom for interactive components) varies.

## Brand Concept
Anime-themed e-commerce storefront (figures, apparel, art prints, manga). Dark base UI (deep navy/near-black) with vibrant accent gradients. Theme toggle included (light/dark, minimum). All imagery/video: AI-generated by us directly (not pulled from third-party explore/community feeds), kept generic/original rather than referencing existing copyrighted franchises.

## Step 1 — Environment & Infrastructure Setup
- [ ] Create single GitHub repo named `inkwake`, single branch
- [ ] Folder structure (3 independent Next.js apps in one repo):
  ```
  /tailwind-app     (own package.json, own postcss/tailwind config)
  /bootstrap-app    (own package.json)
  /strata-app       (own package.json, own strata.config.js)
  ```
- [ ] Install dependencies per app:
  - Tailwind app: `tailwindcss`, `alpinejs` (self-hosted, no CDN)
  - Bootstrap app: `bootstrap` (raw, unpurged, as-shipped)
  - Strata app: `strata-css`
- [ ] Self-host all JS runtimes via `/public` + `<script defer>` (not bundled through webpack, not CDN-linked) for clean, measurable, discrete payloads
- [ ] Create 3 separate Vercel projects (`inkwake-tailwind`, `inkwake-bootstrap`, `inkwake-strata`), each pointed at the same `inkwake` repo with a different Root Directory setting
- [ ] Confirm each project deploys independently and gets its own live domain
- [ ] Sanity-check: push a placeholder "Hello World" page in each app, confirm all 3 domains resolve correctly

## Step 2 — Ink Cursor Effect (Prototype, Standalone)
- [ ] Build and test in isolation, independent of any CSS framework (plain HTML/JS/canvas)
- [ ] Reference behavior: canvas/SVG particle field, ink-style displacement reacting to live cursor position (adapted from the "mist disturbed by breath" reference effect)
- [ ] You test and approve this prototype before it touches any framework build
- [ ] Once approved, this becomes the fixed reference implementation — same JS file, same weight, same behavior — dropped identically into the hero section of all 3 variants later

## Step 3 — Header & Footer (Shared Skeleton)
- [ ] Build Mega Menu (header) + Master Mega Footer in Tailwind → deploy → verify live
- [ ] Rebuild identically in Bootstrap → deploy → verify live matches
- [ ] Rebuild identically in Strata → deploy → verify live matches
- [ ] Confirm theme toggle (light/dark) works correctly in header across all 3 before moving on

## Step 4 — Section-by-Section Build (repeated for each of the 22 sections, top to bottom)
For each section N, in strict order:
1. Build section N in **Tailwind** → push to live Tailwind domain → you verify visually/functionally correct
2. On confirmation, build section N in **Bootstrap** → push to live Bootstrap domain → you verify it matches
3. On confirmation, build section N in **Strata** → push to live Strata domain → you verify it matches
4. Only on full confirmation, proceed to section N+1

No batch-translating sections from memory — each framework's version of a section is built and verified live before starting the next section.

## Step 5 — Asset Swap

## Step 6 — Measurement
- [ ] Tools: Lighthouse/PageSpeed Insights (5+ runs per variant, median), WebPageTest (filmstrip + CSS timing breakdown), Chrome DevTools Performance panel (Recalculate Style / Parse Stylesheet), Network tab (transferred CSS + JS bytes, compression on)
- [ ] Mobile throttling as primary test profile (matches Google's real-world Core Web Vitals signal)
- [ ] Same test location/network conditions across all 3 domains
- [ ] Bootstrap tested as raw/unpurged (as-shipped) — explicitly noted as a "default install" comparison, not an "optimized Bootstrap" comparison
- [ ] Report JS payload cost per framework alongside CSS cost (Bootstrap bundle.js vs Alpine.js vs Strata's runtime) since interactive components use each framework's native idiom

## Open Decisions
- [ ] Placeholder asset realism: real-sized dummy files vs empty colored divs (affects whether early section builds reflect true load behavior)
- [ ] Number of themes: 2 (light/dark) for framework parity, or 3 (light/dark/dim) matching Strata's native default

## Guardrails
- Business logic JS identical across all 3 variants
- UI-state JS (menu toggle, accordion, tabs) uses each framework's native idiom (Bootstrap bundle, Alpine.js, Strata data-st-* attributes) — this is a measured variable, not something to normalize away
- No CDN-hosted assets anywhere — everything self-hosted from the same Vercel origin
- No real anime IP/characters in prompts or copy — original/generic aesthetic only
- AI-generated media: self-generated only, never pulled from third-party explore/community feeds
